# DBService v1.4.1 大查询内存泄漏可能性分析

> 版本：v1.4.1 | 日期：2026-07-31
> 场景：调用方使用 DBService 执行 80 万行（未压缩约 360MB 存储）的大查询，查询完成后内存占用提升且不下降，怀疑内存泄漏。
> 本文档从源码层面分析该场景下 DBService 的内存行为，区分"真泄漏 / 假泄漏"，并给出验证方法。

---

## 一、结论摘要

**DBService 内部未发现会"累积性"增长的真泄漏对象**（所有 QJsonObject/QJsonDocument 均为 Qt 值类型 + 引用计数，生命周期正确）。"内存提升后不再释放"最可能是以下因素的叠加：

| # | 疑似点 | 类型 | 是否真泄漏 |
|---|--------|------|------------|
| 1 | `QJsonDocument(resultObj)` 深拷贝 → 峰值翻倍（~720MB+） | 临时峰值 | 否，会释放 |
| 2 | 360MB 释放后堆碎片 + CRT 缓存，不归还 OS | 假泄漏 | 否，但表现最像泄漏 |
| 3 | 调用方持有结果（存入容器/成员） | 长驻 | **需调用方确认** |
| 4 | DBLogManager 记录了大结果 | 长驻 + 峰值翻倍 | **需调用方确认** |
| 5 | QSqlQuery 结果集缓存 | — | 否（已 setForwardOnly(true)，MySQL 流式取行） |

## 二、大查询内存链路分析（v1.4.1）

```
工作线程：
  executeSqlUnit：逐行 next() → QJsonObject → resultArray.append(std::move(obj))
                  ← resultArray 持有全部 80w 行（≈360MB，结果本身必需的常驻）
  execTask：resultObj[key] = resultArray（引用共享，O(1)）
            → resultJson = QJsonDocument(resultObj)      ★ 深拷贝 → 峰值 ≈ 2×360MB
            → resultArray / resultObj 析构 → 360MB 释放进堆
  emit sigTaskComplete(result)：QueuedConnection 事件，QJsonDocument 引用 +1（O(1)）
主线程：
  onTaskManagerComplete：rawJson = resultJson（引用 +1，O(1)）
  emit sigExecFinished(serviceResult) → 槽返回 → 各引用依次 -1
  → 360MB QJsonDocument 释放进堆 ★ 但 MSVC 堆不还给 OS → "内存不降"
```

**链路中所有对象最终均被释放，不存在"漏掉 delete"的对象。** 内存表现为"升上去不下来"，最符合 **MSVC CRT 空闲块缓存 + 堆碎片** 特征：360MB 由海量小分配（每行每字段一个 QString/QJsonValue）组成，释放后进入空闲链表，后续小分配会复用，但进程常驻内存（Private Bytes / Working Set）不会降。

## 三、分环节内存行为明细

### 3.1 executeSqlUnit（结果构建）

- [qdbconnection.cpp](file:///e:/dev/Project/vibeCoding/utils/DBService/src/DbAccess/QDBConnection/qdbconnection.cpp#L212-L295)
- 逐行 fetch → 构建 QJsonObject → `resultArray.append(std::move(obj))`（v1.4.1 已消除行拷贝）
- `setForwardOnly(true)` 在 `exec()` 之前调用，MySQL 驱动走流式取行，不缓存整表
- 80w 行的 `QJsonArray` 倍增扩容期间存在新旧数组并存（峰值的一部分），释放后形成堆碎片
- **结论**：常驻 ~360MB 为结果本身必需；无泄漏

### 3.2 execTask（结果封装）

- `resultObj[key] = resultArray`：QJsonValue 引用共享，O(1)
- `outResult.resultJson = QJsonDocument(resultObj)`：**深拷贝**，执行期峰值 ≈ 2×360MB（+Qt 内部结构开销，实际可能 1.5~2 倍原始）
- 局部 `resultArray`/`resultObj` 随后析构，360MB 释放进堆
- **结论**：峰值翻倍不可避免（QJsonDocument 语义要求独立所有权），但会释放；是"内存提升"的主要贡献者之一

### 3.3 信号传递（跨线程回调）

- `emit sigTaskComplete(result)`（工作线程）→ QueuedConnection 事件持有 `DBTaskResult`，`QJsonDocument` 引用 +1（O(1)）
- `convertResult` 中 `result.rawJson = taskResult.resultJson`：引用 +1（O(1)），无深拷贝（[dbservice.cpp L257-274](file:///e:/dev/Project/vibeCoding/utils/DBService/src/DBService/dbservice.cpp#L257-L274)）
- 槽处理完毕 → 引用逐级 -1 → 360MB 释放
- **结论**：事件队列滞留是临时的（处理即释放），无泄漏

### 3.4 释放后行为（"不释放"的真正原因）

- 360MB 由海量小分配构成，MSVC CRT 低碎片堆保留空闲块，**不归还 OS**
- 进程 Private Bytes / Working Set 保持高位，但内存**可复用**
- **结论**：假泄漏，DBService 无问题

## 四、需要调用方确认的 3 个点（决定是否真泄漏）

1. **调用方是否持有了结果？**
   `sigExecFinished` 槽内是否将 `result.rawJson` 或 `extractData(result.rawJson)` 的结果存入成员容器（QVector/QMap/全局变量）？若每次查询都存一份 → 每次 +360MB 线性增长，为真泄漏（位置在调用方，不在 DBService）。

2. **是否启用了 DBLogManager 记录查询结果？**
   若将大结果发往 `DBLogManager::sigRequestRecord`：
   - `m_pendingResults` 无上限滞留（30s 才 flush）
   - `buildJsonLine` 中 `result.rawJson.object()` 对 360MB **再深拷贝一次**（[DBLogManager.cpp L200-204](file:///e:/dev/Project/vibeCoding/utils/DBService/src/DBService/DBLogManager.cpp#L200-L204)）
   - 序列化约 360MB 日志文本写盘 → 峰值再翻倍 + 磁盘膨胀
   这是 DBService 内部最可能造成"大查询后内存高"的路径（已列入"内存泄漏潜在风险"P1-3）。

3. **内存曲线形态？**
   连续执行 3~5 次同样大查询，观察任务管理器 Private Bytes：
   - 只升一次后保持稳定 / 增幅远小于单次结果 → 假泄漏（堆缓存），DBService 无问题
   - 每次查询稳定增加 ≈ 300~400MB 且不回落 → 真泄漏，按第 1、2 点定位

## 五、DBService 侧已核实无可疑点的地方

- `executeSqlUnit`：`append(std::move(obj))` 已消除行拷贝（v1.4.1）；`setForwardOnly(true)` 在 `exec()` 前调用，不缓存整表
- `resultJson` / `rawJson` 全程引用计数传递，无隐式深拷贝
- `m_pendingTasks` 正常完成即擦除，单任务不涉及
- 无裸指针、无 `new` 未配对

## 六、可改进项（待确认后实施）

1. **DBLogManager 适配大结果**：`buildJsonLine` 对超过阈值（如 1MB）的 `rawJson` 只记元信息/行数，不做全量深拷贝 + 序列化（消除 3.2 之外的第 2 次峰值翻倍 + 磁盘膨胀）；
2. **`QJsonDocument(resultObj)` 峰值翻倍**：大查询场景可接受（查询本身就要 360MB），可评估"边读边发"的 `sigPartialChunk` 分批方案（P1 遗留项）压低峰值；
3. **调用方确认**：若"持有结果"成立，属调用方代码问题，DBService 侧无需改动。

## 七、判定流程速查

```
内存提升后不降
  ├─ 连续 3~5 次同规模查询
  │    ├─ 内存只升一次后稳定 / 增幅 << 单次结果 → 假泄漏（堆缓存）✓ 无需处理
  │    └─ 每次线性增长 ≈ 单次结果大小 → 真泄漏 ↓
  │         ├─ 槽内是否存入容器？ → 是 → 调用方修复
  │         ├─ 是否开启 DBLogManager 记录大结果？ → 是 → 按第六节第 1 项优化
  │         └─ 均否 → 复测并采集堆快照（VMMap / UMDH）定位
```
