# DBService v1.4.1 内存泄漏潜在风险排查报告

> 版本：v1.4.1 | 日期：2026-07-31
> 对 v1.4.1（合并信号 + 内存优化）全链路代码审查，识别出的内存泄漏 / UB / 崩溃风险清单。

---

## 排查范围

| 模块 | 文件 |
|------|------|
| 服务层 | `src/DBService/dbservice.cpp` / `dbservice.h` |
| 日志层 | `src/DBService/DBLogManager.cpp` / `DBLogManager.h` |
| 任务调度 | `src/DbAccess/DBTaskManager/dbtaskmanager.cpp` / `dbtaskmanager.h` |
| 数据库连接 | `src/DbAccess/QDBConnection/qdbconnection.cpp` / `qdbconnection.h` |
| 数据结构 | `dbtask.h` / `dbtaskresult.h`（均为 Qt 值类型，无裸指针） |

**总体结论**：所有结构体均为 Qt 值类型（隐式共享 + 引用计数），无裸指针分配；风险集中在**对象生命周期管理**与**任务失败路径的清理逻辑**。

---

## P0 — 确定的内存泄漏

### 1. `m_pendingTasks` 条目在任务被拒/丢弃时永不清理（无界增长）

**位置**：
- `dbservice.cpp` `onExecSqlList()`：`m_pendingTasks[task.taskId] = sqlList;` 无条件登记，且不检查 `pushTask` 返回值
- `dbtaskmanager.cpp` `pushTask()`：队列满（REJECT 策略）返回 `false`，任务从未进入队列
- `dbtaskmanager.cpp` `flushBatchBuffer()`：队列满时 `continue` 静默丢弃任务

**泄漏链路**：

```
onExecSqlList() → m_pendingTasks[taskId] = sqlList（无条件登记）
      ↓
pushTask() 队列满（REJECT）返回 false / flushBatchBuffer 丢弃任务
      ↓
任务从未进入队列 → 永远不 emit sigTaskComplete
      ↓
onTaskManagerComplete() 永远不执行 → m_pendingTasks 条目永不擦除
      ↓
每个被拒任务永久持有 QVector<SqlTuple>（含全部 SQL 文本）
```

**影响**：Standard/HighPerf 服务的 REJECT 策略下，长时间高负载时 `m_pendingTasks` 无界增长。

**修改建议**（二选一，推荐前者）：
1. 丢弃/拒绝任务时也补发失败结果的 `sigTaskComplete`（`errCode` 标记"队列满被拒"），让上层照常清理；
2. `onExecSqlList` 检查 `pushTask` 返回值，为 `false` 时主动 `m_pendingTasks.remove(taskId)`。

## P0 — 析构期未定义行为 / 崩溃风险

### 2. `~DBService()` / `init()`：悬垂 `deleteLater` + wait 超时销毁运行中线程

**位置**：
- `dbservice.cpp` `~DBService()`：`m_workerThread->quit(); wait(3000);` 后 `m_taskManager->deleteLater();`
- `dbservice.cpp` `init()`：同样模式 + `m_workerThread->deleteLater();`
- `dbservice.cpp` `init()`：`connect(m_workerThread, &QThread::finished, m_taskManager, &QObject::deleteLater);`

#### a) WorkerThread 模式下对已删除对象再次 `deleteLater`（use-after-free）

```
init() 注册 finished → m_taskManager->deleteLater（自动）
      ↓
线程结束时 Qt 处理该 DeferredDelete → m_taskManager 已被真正删除
      ↓
析构函数中 if (m_taskManager) m_taskManager->deleteLater();  ← 悬垂指针调用，UB
```

#### b) `wait(3000)` 超时场景直接崩溃

- `execTask` 中长 SQL 查询无超时，`quit()` 无法中断执行中的任务；
- `wait(3000)` 超时返回 `false` 后析构继续执行，`m_workerThread`（`this` 的子对象）被 QObject 基类析构直接删除；
- 结果：**"QThread: Destroyed while thread is still running" 崩溃**；
- 若 `init()` 在旧线程仍运行时重建管理器，会出现两条线程同时操作同一数据库。

**修改建议**：
1. 线程关闭改为确定性流程：`quit()` + 无条件 `wait()`（或循环 `wait()` 直到返回 true），不要在超时后继续销毁线程对象；
2. WorkerThread 模式下删掉析构里多余的 `m_taskManager->deleteLater()`（已有 `finished` 自动连接兜底）；
3. 给 SQL 执行加查询超时（如 `query.setQueryTimeout`），避免线程无限卡死在 SQL 上。

## P1 — 设计缺陷导致的内存增长 / 数据竞争

### 3. DBLogManager：线程归属混乱 + `m_pendingResults` 无界增长

**位置**：`DBLogManager.cpp` `start()` / `stop()` / `flushToFile()`

**问题明细**：

| # | 问题 | 后果 |
|---|------|------|
| 1 | `moveToThread(m_workerThread)` 被注释掉 | `onRequestRecord`（QueuedConnection）实际仍在**主线程**执行，与注释声称的"工作线程"不符 |
| 2 | `flushToFile` 通过 **DirectConnection** 在工作线程执行 | 对象方法跑在与线程归属不同的线程，访问 `m_logDir`、文件句柄是数据竞争（互斥锁只保护 `m_pendingResults`） |
| 3 | `m_pendingResults` 无条数上限 | 刷盘速率跟不上入队速率时无界增长（内存增长型泄漏） |
| 4 | `stop()` 主线程 `delete m_flushTimer`（已被 moveToThread） | `wait()` 返回后一般安全，但规范做法是 `deleteLater` 或先移回主线程 |

**修改建议**：
1. 恢复 `moveToThread(m_workerThread)`，`flushToFile` 改回 AutoConnection，所有槽在工作线程执行；
2. `m_pendingResults` 加最大容量（超限丢最旧或拒绝新日志）；
3. `m_logDir` 设置后不再变更，或用 `QReadWriteLock` 保护。

### 4. doConnect 中 `removeDatabase` 的句柄释放依赖 QSqlQuery 及时析构

**位置**：`qdbconnection.cpp` `doConnect()`：`m_db = QSqlDatabase(); QSqlDatabase::removeDatabase(m_connectionName);`

**风险**：`removeDatabase()` 时若存在任何存活 `QSqlQuery`，Qt 不会释放底层句柄并打印 `connection ... is still in use` 警告 → **连接句柄泄漏**。`doConnect` 会在 `execTask` 的 ping 之后、断线重连时被调用。

**现状**：所有 `QSqlQuery` 均为局部变量且各路径都调了 `finish()`，**当前风险较低**。

**修改建议**：保持"查询先析构再移除连接"的纪律，可在 `removeDatabase` 前后加 `QSqlQuery` 活跃数兜底断言/警告。

## P2 — 低概率 / 防御性

### 5. `DBTaskManager::init()` 重复调用会覆盖旧 `m_dbConn`

**位置**：`dbtaskmanager.cpp` `init()`：`m_dbConn = new QDBConnection(this);`

**风险**：`init()` 被调用两次时旧连接指针被覆盖（对象仍有 parent，不会真泄漏，但旧 DB 连接会一直存活到管理器析构）。当前 `DBService::init` 每次都新建 manager，**实际不触发**。

**修改建议**：`init()` 开头判重直接返回，或先 `delete m_dbConn` 再创建。

## 风险汇总

| 优先级 | 问题 | 类型 | 触发条件 |
|--------|------|------|----------|
| P0 | `m_pendingTasks` 被拒任务永不清理 | 确定性泄漏 | REJECT 策略 + 队列持续满载 |
| P0 | 析构悬垂 `deleteLater` + wait 超时销毁运行中线程 | UB / 崩溃 | 服务销毁 / 重新 init |
| P1 | DBLogManager 线程归属错乱 + 无界队列 | 数据竞争 / 内存增长 | 高日志速率 + 慢刷盘 |
| P1 | `removeDatabase` 句柄释放依赖查询析构 | 低概率句柄泄漏 | 断线重连期间存在长生命周期查询 |
| P2 | `init()` 重复调用覆盖旧连接 | 防御性 | 重复调用 init() |

---

## 修复优先级建议

1. **优先修复 P0 两项**（真实泄漏 + 崩溃风险）：
   - 拒绝/丢弃任务时补发失败 `sigTaskComplete`，或检查 `pushTask` 返回值并清理 `m_pendingTasks`；
   - 重构析构/init 的线程关闭流程（确定性 wait + 去除多余 deleteLater + SQL 查询超时）。
2. 其次处理 P1：DBLogManager 线程归属修正 + 队列上限。
3. P2 按需处理。
